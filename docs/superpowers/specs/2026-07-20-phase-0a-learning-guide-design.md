# BridgeHub Phase 0A 手敲学习教程设计

> [!WARNING]
> 这是教程设计说明，不是学习者的操作教程。项目内正文是 `docs/learning/phase-0a-from-scratch.md`；学习者实际阅读 Obsidian 中的《BridgeHub Phase 0A 从零手敲教程》。

## 1. 背景

学习者有软件开发和 Web 应用开发经验，但暂时不熟悉操作系统进程、标准输入输出、管道、异步运行时和 Codex app-server 协议。

学习者的时间成本较高，不希望通过开放式练习自行探索实现方案，而是希望直接采用经过验证的最佳实践代码，通过亲手输入、运行和观察结果建立理解。

## 2. 学习环境

- 手敲项目目录：`/Users/xulei/.dev/bridge-hub`
- 已验证参考项目：`/Users/xulei/.dev/bridgehub`
- 学习者已经亲自完成 `git init` 并建立 `learn-develop` 学习分支；后续 Cargo 命令、Git 命令、测试和真实 Codex 验证仍由学习者亲自执行。
- Codex 不代替学习者执行教程中的项目命令，不代替学习者创建 Cargo/Rust 项目文件，也不代替学习者输入项目代码。
- Codex 只负责在手敲目录中维护教程和相关学习文档。

两个目录必须保持独立。`bridgehub` 作为已经验证的标准答案保留，`bridge-hub` 作为学习者从零实现的练习项目。

## 3. 教程目标

学习者按照教程完成后，应当能够亲手实现并解释以下闭环：

1. 使用 Cargo 建立 Rust Workspace 和独立 Crate。
2. 理解程序文件、进程、父进程和子进程的区别。
3. 理解 stdin、stdout、stderr 和本机管道的作用。
4. 理解 JSON、JSONL、请求、响应和通知的区别。
5. 使用 Tokio 与 `process-wrap` 启动并拥有 Codex app-server 进程树。
6. 发送 `initialize` 请求并解析类型化响应。
7. 发送 `initialized` 通知，完成协议握手。
8. 异步读取 Codex stderr，避免子进程因缓冲区写满而阻塞。
9. 给握手和自然退出分别设置期限；失败时仍统一关闭管道、终止整棵进程树并等待回收。
10. 使用测试、格式检查和 Clippy 验证实现。

## 4. 范围

教程只覆盖已经验证的 Phase 0A：Codex app-server 初始化握手。

教程不包含：

- Thread 创建与恢复。
- Turn 启动与多轮对话。
- 流式 Item 和 Tool Calling。
- Approval 和 Interrupt。
- Session 持久化。
- Local Connector、Public Relay 和 Web 页面。
- 录音、文件或图片上传。

这些内容必须在 Phase 0A 由学习者亲手完成、能够按设计依据解释并通过验证后，再通过后续教程逐步加入。学习者不需要脱离教程独自猜测架构。

## 6. 教学方式与工程决策责任

教程采用“Codex 负责设计、设计先于代码、学习者分段手敲、完成后立即验证”的方式。

学习者当前不需要先具备工程设计能力，也不需要在多个技术方案中自行猜测答案。Codex 负责根据当前项目目标、官方文档、依赖源码、真实运行约束和初学者认知成本作出技术选择；教程负责把这段工程推理完整展示出来。这里的“讨论”是把候选方案、选择依据和代价讲清楚，不是把决定重新交给学习者。

只有产品目标、费用、安全授权和数据边界等不能由技术事实代替用户决定的事项，才需要暂停并询问学习者。架构、模块边界、类型设计、异步模型、错误处理、依赖、测试方式和进程生命周期默认由 Codex 直接决定。

### 6.1 “最佳实践”的选择标准

技术选择按以下顺序判断：

1. 与当前官方 API、依赖源码和真实运行行为一致。
2. 不使用只为演示而存在、放进真实项目就必须推翻的错误写法。
3. 只建立当前阶段需要的最小完整架构，不提前加入 Relay、数据库或通用框架。
4. 能通过测试、日志、退出状态或真实运行结果观察和验证。
5. 能帮助初学者形成正确心智模型，而不是隐藏关键机制。
6. 保留清晰的后续演进边界，但不为假设需求提前抽象。

“最适合初学者”不等于“代码最少”。如果资源回收、错误分层或协议顺序是正确实现不可缺少的内容，教程必须保留并解释，不能为了短而删除。

### 6.2 每个学习单元的固定结构

每个有意义的代码或配置阶段固定包含：

1. **当前状态**：项目做到哪里，已有能力是什么。
2. **要解决的问题**：这一步为什么存在，不做会发生什么。
3. **本步目标与非目标**：完成后新增什么，哪些内容明确推迟。
4. **基础心智模型**：先用应用开发者熟悉的概念解释新知识。
5. **工程约束与不变量**：协议顺序、所有权、资源生命周期等不能破坏的规则。
6. **候选方案**：通常列出 2–3 个真实可行方案；跨产品边界的比较最多 4 个。不能虚构明显错误的陪衬方案。
7. **最终选择**：Codex 直接给出结论，并解释选择依据。
8. **代价与后续演进**：说明当前选择放弃了什么、什么时候需要升级。
9. **数据流或执行顺序**：必要时使用小型架构图或时序图。
10. **可观察行为**：写代码前先说明测试要证明什么、运行时应该看到什么。
11. **完整命令与代码**：由学习者亲自输入，不留省略号或待补空白。
12. **语法与逐行解释**：解释 Rust/TOML/Shell 语法以及它在设计中的职责。
13. **验证与排错**：运行命令、预期结果、失败分类和最短排查路径。
14. **设计回看**：指出前面的每项设计决定最终落在哪段代码中。
15. **完成检查框**：方便学习者中断后继续。

核心设计理由必须留在主教程中，不能只藏在外链笔记。较深的 Rust 语法、操作系统原理和延伸内容保存到 Obsidian 学习笔记，并通过 WikiLink 与主教程双向关联。

每次创建或修改文件之前，教程必须先单独写明：

- 文件相对于项目根目录的位置。
- 文件的绝对路径。
- 该文件在目录树中的层级。
- 使用 Neovim 打开或创建它的完整命令。

不能只写“创建某文件”，也不能假设学习者知道“根目录”具体指哪里。

教程不设置需要学习者自行设计答案的开放式作业。可以加入简短的理解检查，但答案必须紧随其后，不增加不必要的思考等待。

## 7. 代码呈现规则

### 7.1 完整可运行

每个代码阶段都必须能直接编译，或者被明确标记为 TDD 中“预期编译失败”的阶段。不能使用省略号、伪代码、`TODO` 或要求学习者自行补全的空白。

### 7.2 注释放在代码内部

Rust 使用 `//`，TOML 和 Shell 使用 `#`。每一行新代码都必须在代码块内部获得解释；只包含括号或符号的结构行，也要在它附近解释其作用。注释直接解释下一行代码或当前参数，使学习者可以一边手敲一边理解。

示例：

```rust
// pub 表示其他模块可以调用这个函数。
// const fn 表示这个函数可以在编译期求值。
// -> &'static str 表示返回值在整个程序运行期间都有效。
pub const fn client_name() -> &'static str {
    // Rust 会把最后一个没有分号的表达式作为函数返回值。
    "bridgehub"
}
```

### 7.3 不用术语解释术语

第一次出现专业词汇时，必须先用应用开发者熟悉的概念解释，再给出正式定义。例如先将 stdin/stdout 类比为本机程序之间的请求和响应方向，再解释它们是操作系统提供的标准流。

### 7.4 保留工程最佳实践

为降低理解难度，教程可以拆小步骤，但最终实现不得故意使用错误或过时的工程方式。需要保留：

- Rust 2024 Edition 和固定工具链。
- Workspace 依赖集中管理。
- 禁止 `unsafe`、`unwrap` 和 `expect`。
- Serde 类型化序列化与反序列化。
- thiserror 类型化错误。
- Tokio 异步进程与 I/O。
- tracing 日志，并显式写入 stderr，避免污染 CLI 的 stdout 结果。
- `process-wrap` 的 Unix 进程组 / Windows Job Object、握手期限、退出宽限期、`start_kill` 和 `wait` 回收。
- 成功、协议错误和超时都经过统一清理；`KillOnDrop` 只作为直接 Child 的意外析构兜底，不冒充完整进程树保证。
- 测试先失败、最小实现后通过的 TDD 过程。

### 7.5 设计说明必须出现在代码之前

不能在一大段代码之后才补一句“为什么这样做”。每次引入新的配置文件、公共类型、异步任务、子进程或资源清理路径之前，必须先使用下面的语义结构说明设计：

```markdown
> [!question] 要解决的问题
> 说明当前缺口和不处理的后果。

> [!abstract] 约束与不变量
> 说明不能被破坏的协议、类型或生命周期规则。

> [!example] 候选方案
> 简要比较真实可行的方案。

> [!success] 本教程的选择
> 直接给出选择、依据和它如何服务当前阶段。

> [!warning] 代价与暂不实现
> 说明当前方案的成本和明确推迟的内容。
```

小步骤可以合并其中若干块，但“问题、选择、原因、代价”四项不能缺失。代码之后再增加“设计落点”，把设计语言映射回具体类型、函数和测试。

## 9. 错误处理

教程覆盖最常见的学习阻塞：

- 当前目录错误。
- Rust 工具链未安装或版本不一致。
- Cargo 找不到 Workspace 成员。
- Crate 名称与 `use` 路径不一致。
- 测试在预期失败阶段没有失败。
- JSON 字段命名不匹配。
- Codex 路径错误。
- Codex 未安装或未完成认证。
- app-server 提前退出。
- initialize 握手超时。
- 超过自然退出宽限期并进入强制终止路径。
- Clippy 因 `unwrap`、`expect` 或未使用内容失败。

错误说明先帮助学习者识别“这是教程预期的失败”还是“输入错误导致的意外失败”，再给出最短排查路径。

## 10. 验证策略

教程以 `/Users/xulei/.dev/bridgehub` 中已经通过验证的 Phase 0A 代码作为起始基线，但不能把参考实现当成无需复核的权威。Codex 协议必须直接核对 sibling `../codex` 当前源码；依赖行为必须核对依赖文档或源码；进程生命周期必须用与教程最终代码相同的临时验证 Crate 编译和真实 Smoke Test。若基线会误导学习者，教程应直接采用有依据且不扩大阶段范围的修正，并在设计说明和内部计划记录差异。

当前已经确认的基线修正：

1. 本机 `/opt/homebrew/bin/codex` 是 Node 启动包装器，还会创建原生 Codex 后代；只终止 Tokio 直接 `Child` 不能构成进程树保证。
2. 使用维护中的 `process-wrap 9.1`：Unix 使用 `ProcessGroup::leader()`，Windows 使用 `JobObject`，并保留 Tokio 原始标准流。
3. `command-group` 已弃用，且它的 Unix `kill_on_drop` 不满足整组兜底要求，因此不进入新教程。
4. `handshake(...).await?` 不能无限等待，也不能在错误时绕过清理；最终实现使用 10 秒握手期限、先保存结果、统一清理、最后传播错误。
5. 自然退出宽限期使用 `try_wait + sleep`；不对 `process-wrap` 的组感知 `wait` Future 使用可取消 timeout。
6. tracing 显式写父进程 stderr；Codex stderr 无论日志 Filter 是否显示都持续排空。

上述最终代码已在独立临时 Crate 中通过 rustfmt、Clippy `-D warnings`、6 个测试和本机 Codex 0.144.1 真实握手；这份验证不能替代学习者按教程在自己的 `learn-develop` 分支亲自运行。

编写教程时需要确认：

- 所有路径在从零创建的目录结构中一致。
- 所有代码块完整，没有省略内容。
- 带中文注释的代码仍是合法 Rust、TOML 或 Shell。
- 红色阶段的失败原因与教程描述一致。
- 绿色阶段的测试数量与预期一致。
- 最终真实命令与 `bridgehub-codex-spike` CLI 参数一致。
- 文档内部链接和章节引用有效。

Codex 不在 `/Users/xulei/.dev/bridge-hub` 中执行项目命令。学习者根据教程亲自执行，并把实际输出或错误发回当前对话，由 Codex继续解释和指导。

## 11. 完成标准

教程完成必须同时满足：

- 学习者不需要自行补代码或猜命令。
- 每个新概念都在第一次使用前解释。
- 每一段代码都说明其输入、输出和运行位置。
- 每个文件在创建前都提供相对路径、绝对路径、目录层级和 Neovim 命令。
- 所有关键代码行都能在代码块内部找到中文解释。
- 每个有意义的代码或配置阶段都先说明问题、候选方案、最终选择、原因和代价。
- 技术方案由 Codex 直接选定，不要求学习者先完成开放式工程设计。
- 设计决定能够在后续代码和测试中找到明确落点。
- 协议成功路径以及 EOF、错误 ID、服务端错误三个关键失败分支均有行为测试。
- 成功、握手错误和握手超时均进入同一进程树清理主干；教程不把直接 Child 兜底描述成完整进程树保证。
- 每个步骤都有明确的成功或预期失败信号。
- 教程完整覆盖当前 Phase 0A 实现。
- 教程没有提前混入 Phase 0B 或完整 BridgeHub 架构。
- 所有项目命令与代码都由学习者亲自输入和执行。
